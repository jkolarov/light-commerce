# Phase 1 (demo site) implementation plan

> **For agentic workers:** the tasks live in Linear (team Fluxory, project "Lightweight commerce", milestone "Phase 1: Demo site"). One Linear story = one branch = one PR. This file holds what tickets share: constraints, the failure modes reviewers check, the names and signatures that tickets running in parallel must agree on, and the dependency map. Inside a story, work test-first (superpowers:test-driven-development). If a story needs a step-by-step plan, write it in your branch with superpowers:writing-plans.

**Goal:** a complete demo site for a fictional company at `lightcommerce.fluxory.dev`: a few CMS pages, a few products, a working Stripe test-mode checkout, order emails.

**Architecture:** one Next.js app with Payload 4 inside it. `core` (config, users, media, email, i18n) plus two Payload plugins in the repo, `cms` and `shop`. Each plugin works without the other. `shop` wraps Payload's official ecommerce plugin. `light.config.ts` holds owner-facing settings; `payload.config.ts` only composes.

**Tech stack:** Payload 4 (beta, exact version pinned), `@payloadcms/plugin-ecommerce` (exact version pinned), `@payloadcms/db-sqlite`, Next.js 16.4+, React 19, TypeScript 6, Node.js 24, pnpm, zod, next-intl, Tailwind 4, vitest, Playwright, Docker.

**Spec:** `docs/superpowers/specs/2026-11-03-light-commerce-design.md`. Stack decision: `docs/adr/0001-stack.md`.

## Global constraints

- Payload 4 and `@payloadcms/plugin-ecommerce` pinned to exact versions; each upgrade is its own ticket.
- Node.js 24, Next.js 16.4+, TypeScript 6, SQLite.
- Money is integer cents (minor units).
- FR and EN from the start. Content uses Payload localization with fallback to the default locale (S02 sets it up with `fr`/`en` hardcoded, S06 wires it to `light.config.ts`); public UI strings live in `messages/{fr,en}.json`; URLs are prefixed by locale (`/fr/...`, `/en/...`).
- One installation per site. No `organizationId`, no tenant field.
- Card fields are always drawn by the payment provider. No provider SDK outside `src/modules/shop/payments/<provider>/`.
- Stripe's webhook is the source of truth for orders. Order creation is idempotent.
- `cms` and `shop` each start, typecheck, build and pass unit tests with the other switched off. They never import each other.
- No email leaves the demo: every email goes to Mailpit.
- The demo is hidden from search engines.

## Review focus

The five failure modes the spec implies that are most likely to bite. Each is pinned by a test in the story that owns the code.

1. **Payment confirmed twice, or the browser never returns.** The browser confirm and the webhook both run, the webhook is retried, or only the webhook arrives. Expected: exactly one order, stock decreased once. Owner: S18.
2. **Tampered amounts.** A request that sends its own prices or totals must not change what is charged. The amount is computed on the server from stored prices plus shipping. Owner: S17.
3. **The last item in stock.** Two carts, one unit left. Checkout re-checks stock before creating the payment. If stock runs out after a successful payment, the order is still created and flagged for the owner, and stock never goes below 0. Owners: S17, S18.
4. **Guessable order pages.** The confirmation page shows an order only with its unguessable access token, never by trying IDs. Owner: S18.
5. **A missing translation.** A page or product without EN text shows the FR text (fallback to the default locale), never a blank page or an error. Owners: S02 (fallback on), S09 (test).

### Collections, blocks, routes

- Core collections: `users`, `media`. CMS: collection `pages`, globals `header` and `footer`. Shop: the ecommerce plugin's collections, with their default slugs: `products`, `variants`, `variantTypes`, `variantOptions`, `carts`, `orders`, `transactions`, `addresses`. The plugin's customers collection is `users` (`ecommercePlugin({ customers: { slug: 'users' } })`); there is no separate customers collection.
- Admin (S13): `carts`, `addresses`, `variants`, `variantTypes`, `variantOptions` get `admin.hidden: true`; `transactions` is read-only (`access.create/update/delete: () => false`, `admin.group: false`). All through the plugin's `*CollectionOverride` options.
- Shop REST endpoints the plugin adds (fixed by the plugin): `POST /api/payments/stripe/initiate`, `POST /api/payments/stripe/confirm-order`, `POST /api/payments/stripe/webhooks` (the Stripe webhook route), and `POST /api/carts/:id/add-item`, `/update-item`, `/remove-item`, `/clear`. Guest carts are reached with the cart's `secret`.
- Blocks: `hero`, `richText`, `imageText`, `callToAction` (cms); `productGrid` (shop, added to `pages` only when `pages` exists).
- The home page is the page with slug `home`. Page slugs are localized. Products have one slug shared by both locales.
- Routes under `src/app/(frontend)/[locale]/`:
  - `page.tsx`: home. The CMS `home` page, or the shop's `ProductList` when the CMS is off. Owner: S09 (wired against the stub; S15 fills `ProductList`).
  - `[...slug]/page.tsx`: CMS pages. Owner: S09.
  - `shop/page.tsx`, `shop/[slug]/page.tsx`: S15. `cart/page.tsx`: S16. `checkout/page.tsx`: S17. `order/[id]/page.tsx`: S18.
  - `layout.tsx`: S22, wired against the `frontend.ts` stubs. No module story edits it.

`users.roles: ('owner' | 'staff')[]`. Helpers in `src/core/access/index.ts`: `anyone`, `isOwner`, `isStaffOrOwner`, `publishedOrStaff` (published documents for everyone, drafts for staff). ### Money and shipping (S13, S14)

- Prices are integer cents, stored by the plugin: `products.priceInEUR` (and `variants.priceInEUR`) with its switch `priceInEUREnabled`, `products.inventory` (integer). Cart `subtotal`, transaction `amount` and order `amount` are integer cents; the currency code is `'EUR'`, configured with the plugin's `EUR` export (`currencies: { supportedCurrencies: [EUR], defaultCurrency: 'EUR' }`).
- Shipping is added to the charged amount in `src/modules/shop/payments/stripe/` by wrapping the Stripe adapter's `initiatePayment` (it adds the shipping amount to `cart.subtotal`). The plugin has no shipping of its own.
- `src/modules/shop/money.ts`: `formatMoney(cents: number, opts: { currency: string; locale: Locale }): string`
- `src/modules/shop/shipping/calculate.ts`: `calculateShipping(input: { subtotal: number }, shipping: ShopConfig['shipping']): { method: 'flat'; amount: number }`

### Orders (S18)

- `orders.accessToken`: random, at least 128 bits, set when the order is created. Confirmation URL: `/[locale]/order/[id]?token=<accessToken>`. Without the right token the page returns 404. The name matters: the plugin's `confirm-order` response includes `accessToken` when the orders collection has this field.
- `orders.subtotal: number` and `orders.shippingAmount: number` (cents; added by the shop through `ordersCollectionOverride`, because the plugin's order only has `amount`, the charged total, and its `items` carry no prices). Invariant: `subtotal + shippingAmount === amount`. S17 computes both at payment start with `calculateShipping` (S14) and stores them on the transaction (`transactions.subtotal`, `transactions.shippingAmount`); S18 copies them onto the order when it is created. The order is always created inside the plugin's `confirm-order` handler, on the browser path and through `finalizePayment` alike, so the copy happens in the Stripe adapter wrapper: its `confirmOrder` passes them into the plugin's `finalizeOrder` as extra `orderData` (verified in the spike on browser, webhook-only and 12-way race paths). S18's confirmation page and S19's emails show subtotal and shipping separately.
- `orders.needsAttention: boolean` and `orders.attentionNote: string`: set when something needs the owner, for example stock ran out after a successful payment. Shown in the admin's order list.
- `src/modules/shop/orders/finalizePayment.ts`: `finalizePayment(payload: Payload, paymentIntentId: string): Promise<{ order: Order; created: boolean }>`. It is idempotent. The browser confirm path is the plugin's own `POST /api/payments/stripe/confirm-order`; the `payment_intent.succeeded` webhook handler calls `finalizePayment`, which runs that same endpoint's handler (found in `payload.config.endpoints`), so both paths share the plugin's atomic transaction claim. The plugin's internal `finalizeOrder` is not exported. The endpoint's response does not say whether this call created the order, so `created` can only be derived (for example from the transaction's status before the call) and is not reliable under a race: send emails once through `orders.confirmationEmailSentAt`, not through `created`.
- `orders.confirmationEmailSentAt: Date | null` (S19): emails go out once per order.
- Rule (S13, S18): the SQLite adapter keeps its default of **no database transactions**: no `transactionOptions` in `sqliteAdapter(...)`. The plugin's atomic transaction claim keeps orders unique; turning transactions on caused `SQLITE_BUSY` failures and an order that was confirmed but never committed (ADR 0001, "Findings").
- Rule (S17, S18): the Stripe adapter wrapper lives in `src/modules/shop/payments/stripe/` (spike model: `src/modules/shop/payments/stripe/index.ts` on `spike/payload-v4`). It relies on plugin internals that every plugin upgrade re-checks: the `/payments/stripe/confirm-order` handler found in `payload.config.endpoints` (fed `req.data` with `paymentIntentID`, `cartID`, `customerEmail`, `secret`), the guest cart `secret` read with `payload.db.findOne`, and the `finalizeOrder` callback the plugin passes to the adapter's `confirmOrder`.

### Environment (`.env.example`, created by S02, extended by each story that adds a variable)

`PAYLOAD_SECRET`, `DATABASE_URI` (default `file:./data/light.db`), `NEXT_PUBLIC_SERVER_URL`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `STRIPE_SECRET_KEY`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`, `STRIPE_WEBHOOKS_SIGNING_SECRET` (confirmed by S01: the plugin takes `webhookSecret` as an option, and this is the name its docs and templates use), `SEED_OWNER_EMAIL`, `SEED_OWNER_PASSWORD`.

### Scripts (`package.json`, created by S02)

`dev`, `build`, `start`, `typecheck`, `lint`, `test` (vitest), `generate` (Payload types + admin import map), `generate:check` (fails if generated files are stale), plus `seed` (S23) and `test:e2e` (S25).

- `build` is `payload build`: it runs `payload generate:importmap` and `payload generate:types`, then `next build`.
- `generate` runs `payload generate:types` and `payload generate:importmap`. The generated files, and the only ones `generate:check` compares, are `src/payload-types.ts` and `src/app/(payload)/admin/importMap.js`. Payload 4 does not regenerate the other files in `src/app/(payload)/`. `payload generate:db-schema` (`src/payload-generated-schema.ts`) is not used.
