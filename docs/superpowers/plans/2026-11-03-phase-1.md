# Phase 1 (demo site) implementation plan

> **For agentic workers:** the tasks live in Linear (team Fluxory, project "Lightweight commerce", milestone "Phase 1: Demo site"). One Linear story = one branch = one PR. This file holds what tickets share: constraints, the failure modes reviewers check, the names and signatures that tickets running in parallel must agree on, and the dependency map. Inside a story, work test-first (superpowers:test-driven-development). If a story needs a step-by-step plan, write it in your branch with superpowers:writing-plans.

**Goal:** a complete demo site for a fictional company at `lightcommerce.fluxory.dev`: a few CMS pages, a few products, a working Stripe test-mode checkout, order emails.

**Architecture:** one Next.js app with Payload 4 inside it. `core` (config, users, media, email, i18n) plus two Payload plugins in the repo, `cms` and `shop`. Each plugin works without the other. `shop` wraps Payload's official ecommerce plugin. `light.config.ts` holds owner-facing settings; `payload.config.ts` only composes.

**Tech stack:** Payload 4 (beta, exact version pinned), `@payloadcms/plugin-ecommerce` (exact version pinned), `@payloadcms/db-sqlite`, Next.js 16.4+, React 19, TypeScript 6, Node.js 24, pnpm, zod, next-intl, Tailwind 4, vitest, Playwright, Docker.

**Spec:** `docs/superpowers/specs/2026-11-03-light-commerce-design.md`. Stack decision: `docs/adr/0001-stack.md`.

## Global constraints

- Payload 4 and `@payloadcms/plugin-ecommerce` pinned to exact versions; each upgrade is its own ticket.
- Node.js 24, Next.js 16.4+, TypeScript 6, SQLite.
- Money is integer cents (minor units).
- FR and EN from the start. Content uses Payload localization with fallback to the default locale (S02 sets it up with `fr`/`en` hardcoded, S06 wires it to `light.config.ts`); public UI strings live in `messages/{fr,en}.json`; URLs are prefixed by locale (`/fr/...`, `/en/...`).
- One installation per site. No `organizationId`, no tenant field.
- Card fields are always drawn by the payment provider. No provider SDK outside `src/modules/shop/payments/<provider>/`.
- Stripe's webhook is the source of truth for orders. Order creation is idempotent.
- `cms` and `shop` each start, typecheck, build and pass unit tests with the other switched off. They never import each other.
- No email leaves the demo: every email goes to Mailpit.
- The demo is hidden from search engines.

## Review focus

The five failure modes the spec implies that are most likely to bite. Each is pinned by a test in the story that owns the code.

1. **Payment confirmed twice, or the browser never returns.** The browser confirm and the webhook both run, the webhook is retried, or only the webhook arrives. Expected: exactly one order, stock decreased once. Owner: S18.
2. **Tampered amounts.** A request that sends its own prices or totals must not change what is charged. The amount is computed on the server from stored prices plus shipping. Owner: S17.
3. **The last item in stock.** Two carts, one unit left. Checkout re-checks stock before creating the payment. If stock runs out after a successful payment, the order is still created and flagged for the owner, and stock never goes below 0. Owners: S17, S18.
4. **Guessable order pages.** The confirmation page shows an order only with its unguessable access token, never by trying IDs. Owner: S18.
5. **A missing translation.** A page or product without EN text shows the FR text (fallback to the default locale), never a blank page or an error. Owners: S02 (fallback on), S09 (test).

### Money and shipping (S13, S14)

- Prices are integer cents by convention: `products.priceInEUR` (and `variants.priceInEUR` if variants are on) with its switch `priceInEUREnabled`, and `products.inventory`. The plugin's price and amount fields are plain `number` fields (SQLite `numeric`) with no integer check, and only the admin's price input converts euros to cents. So S13 adds an integer validator (`Number.isInteger`, ≥ 0) to `priceInEUR` on products (and variants if enabled) through the overrides. Cart `subtotal`, transaction `amount` and order `amount` are cents; the currency code is `'EUR'`, configured with the plugin's `EUR` export (`currencies: { supportedCurrencies: [EUR], defaultCurrency: 'EUR' }`).
- Shipping is added to the charged amount in `src/modules/shop/payments/stripe/` by wrapping the Stripe adapter's `initiatePayment`: it prices the cart again with `priceGuestCart` (today's stored prices plus `calculateShipping`) and hands the inner adapter that `total` as `cart.subtotal`. The stored `carts.subtotal` is never charged (see "Cart (S16)"). The plugin has no shipping of its own.
- `src/modules/shop/money.ts`: `formatMoney(cents: number, opts: { currency: string; locale: Locale }): string`
- `src/modules/shop/shipping/calculate.ts`: `calculateShipping(input: { subtotal: number }, shipping: ShopConfig['shipping']): { method: 'flat'; amount: number }`

### Cart (S16)

- The guest's cart is in the httpOnly, SameSite=Lax cookie `lc_cart`, value `<cartId>.<secret>`. `src/modules/shop/cart/cookie.ts`: `readCartRef(): Promise<CartRef | null>`, `saveCartRef(ref)`, `forgetCartRef()` (the last two in Server Actions and Route Handlers only). httpOnly keeps the secret from page scripts, not from the visitor: it is their cookie, and with it they can change their own cart over the plugin's REST endpoints, in any way `checkCartItems` allows. So server code never trusts what a cart holds or what it says it costs. The site's pages and actions read the cart from the cookie on the server; the checkout (S17) starts the payment on the server too, giving the plugin's `initiate` handler `cartID` and `secret` from the cookie.
- Every cart write runs `checkCartItems` (`cart/checkItems.ts`, carts `beforeChange`, first): the currency is always `shop.currency`; what a write grows must be a published product with a price, within its stock and `MAX_LINE_QUANTITY` (99), one line per product, at most `MAX_CART_LINES` (8) lines (what one Stripe payment can carry, see "Checkout (S17)"). What a write leaves alone or shrinks is not checked, so the plugin's own write on confirmation (`purchasedAt`) never throws. The plugin itself checks stock only when a payment starts.
- **What S17 charges:** `priceGuestCart(payload, cart): Promise<CartPricing>` (`cart/load.ts`) reads the cart's products as visitors read them now and prices them with the pure `priceCart(items, products, shop)` (`cart/price.ts`), the same rules as the cart page: `subtotal` from current stored prices, `shipping` from `calculateShipping`, `total = subtotal + shipping`, and `canCheckout` false for an empty cart or any line with a `problem` (`lineProblem` in `cart/rules.ts`: no longer for sale, sold out, not enough stock, over 99). S17 calls it on `data.cart` inside the Stripe adapter wrapper's `initiatePayment`, refuses the payment unless `canCheckout`, charges `total`, and stores `subtotal` and `shipping` as the transaction's `subtotal` and `shippingAmount`. It never uses `carts.subtotal`: the plugin writes that at the last cart change, so it goes stale after a price change, still counts a line whose price was switched off, and can be anything a broken write left (it was NaN in a review probe).
- `src/modules/shop/cart/load.ts` also has `findGuestCart(payload, ref): Promise<Cart | null>` (null for a wrong secret or a bought cart) and `cartView(payload, cart, locale): Promise<CartView>` (the pricing plus names, photos and links, for the pages).
- `cartPath(locale)`, `checkoutPath(locale)` in `cart/paths.ts`. A bought cart (`purchasedAt` set) counts as no cart, and the next add starts a new one; the confirmation may also call `forgetCartRef()`.

### Checkout (S17)

- Routes (shop): `/[locale]/checkout` (the page), `/[locale]/checkout/return` (a GET route handler: Stripe's `return_url`, and where the form sends the browser after a card payment), `/[locale]/checkout/received` ("payment received"; `?checking=1` when the server could not tell). The checkout hides the site header while it is on the page (`[data-lc-checkout]`), and keeps the site footer.
- The form mounts Stripe's Payment Element before any payment exists (deferred intent, `usePaymentElement` in `payments/stripe/`), with the total the page shows. On Pay, the Server Action `startPayment({ details, expectedTotal })` (`checkout/actions.ts`) checks the details (`checkDetails`, `checkout/details.ts`), reads the cart from the cookie, and calls the plugin's `initiate` handler in-process (`startStripePayment`, `payments/stripe/payments.ts`). `expectedTotal` only decides whether to go on: the wrapper refuses a cart that costs anything else (`req.context.lightCheckout`), and the visitor goes back to `/[locale]/cart?notice=changed`.
- The Stripe wrapper (`withCheckoutRules`, `payments/stripe/wrap.ts`) refuses a payment that doesn't come from the checkout: the plugin's public `POST /api/payments/stripe/initiate` has no `req.context.lightCheckout`, so it is refused, and its address and email rules can't be skipped. It re-checks the email and shipping address with `checkDetails`, and hands the inner adapter fresh line ids on each attempt (the plugin copies line ids into `transactions.items`, whose ids are a primary key, so a second attempt on one cart would fail).
- Line limit: the plugin's Stripe adapter stores every cart line in one PaymentIntent metadata value (`cartItemsSnapshot`), about 61 characters per line, and Stripe caps a value at 500 characters. So a cart holds at most 8 lines (`MAX_CART_LINES`), and the wrapper refuses a snapshot over 500 characters before calling Stripe (`tooManyLines`; the visitor is told to remove some products). Moving the snapshot off Stripe's metadata is a backlog ticket.
- The return path runs `confirmCheckout(payload, { paymentIntentId, cart })` (`checkout/confirm.ts`): it asks Stripe first (`paymentOutcome`); for a paid PaymentIntent and the browser holding the payment's cart it calls the plugin's `confirm-order` handler (`confirmStripePayment`), so the wrapper's `confirmOrder` settles it; then `outcomePath` sends the browser to `/[locale]/order/[id]?token=` (S18: the order's page, via `finalizePayment`), to "payment received" when no order came back after a paid PaymentIntent (the webhook creates it), and back to the checkout with `?payment=failed` when it was not paid. A browser without the cart learns only whether the payment went through.

### Orders (S18)

- `orders.accessToken`: random, at least 128 bits, set when the order is created. Confirmation URL: `/[locale]/order/[id]?token=<accessToken>`. Without the right token the page returns 404. The name matters: the plugin's `confirm-order` response includes `accessToken` when the orders collection has this field.
- `orders.subtotal: number` and `orders.shippingAmount: number` (cents, because the plugin's order only has `amount`, the charged total, and its `items` carry no prices). S18 adds the orders fields and S17 adds `transactions.subtotal` and `transactions.shippingAmount`, both through the collection overrides in `src/modules/shop/collections/`. Invariant: `subtotal + shippingAmount === amount`. S17 computes both at payment start with `calculateShipping` (S14) and stores them on the transaction (`transactions.subtotal`, `transactions.shippingAmount`); S18 copies them onto the order when it is created. The order is always created inside the plugin's `confirm-order` handler, so the copy happens in the Stripe adapter wrapper: its `confirmOrder` passes them into the plugin's `finalizeOrder` as extra `orderData`. S18's confirmation page and S19's emails show subtotal and shipping separately.
- `orders.needsAttention: boolean` and `orders.attentionNote: string`: set when something needs the owner, for example stock ran out after a successful payment. Shown in the admin's order list.
- Stock (S18): the plugin decrements stock with a raw `$inc` that skips `min: 0` and hooks, and `confirm-order` does not re-check stock. So before calling the plugin's `finalizeOrder`, the wrapper's `confirmOrder` checks stock and, if it is short, sets `needsAttention` and `attentionNote` in `orderData`. Afterwards it clamps any stock below 0 back to 0 and flags that order too: two carts paying for the last unit at the same moment both pass the first check. A `min: 0` on the field or a products hook does not help. (How: "Built in S18", below.)
- `src/modules/shop/orders/finalizePayment.ts`: `finalizePayment(payload: Payload, paymentIntentId: string): Promise<{ order: Order }>`. It is idempotent. The webhook handler and the browser's return path both call it; it runs the plugin's `confirm-order` handler (found in `payload.config.endpoints`), so every path shares the plugin's atomic transaction claim. The plugin's public `POST /api/payments/stripe/confirm-order` stays open and goes through the same claim. The plugin's internal `finalizeOrder` is not exported. `finalizePayment` returns no `created` flag, because the endpoint does not say which call created the order.
- `orders.confirmationEmailSentAt: Date | null` (S19): emails go out once per order. S19 sends them outside the confirm-order request, never from a hook that runs during settlement. It claims each order with an atomic conditional update that sets `confirmationEmailSentAt` only where it is still empty (`payload.db.updateOne(..., { options: { atomic: true } })`, as the plugin does; no DB transactions).
- Rule (S13, S17, S18, S19): no hook may block or throw during settlement (orders create hooks, carts and transactions update hooks). The plugin's losing confirm calls wait only 500 ms and then answer 500. An error after the claim leaves the transaction in `processing` for good, and every later confirm, webhook retries included, fails. S17 treats a confirm-order 500 after a succeeded PaymentIntent as "payment received, order pending", not as a failed payment.
- Rule (S02, S13, S18): the SQLite adapter is `sqliteAdapter({ client: { url: process.env.DATABASE_URI }, busyTimeout: 5000, wal: true })` with **no `transactionOptions`**, so no database transactions (the adapter's default). This is the combination that passed the spike's races; turning transactions on caused `SQLITE_BUSY` failures and an order that was confirmed but never committed (ADR 0001, "Findings"). S08 adds `prodMigrations`.
- Rule (S17, S18): the Stripe adapter wrapper lives in `src/modules/shop/payments/stripe/` (spike model: `src/modules/shop/payments/stripe/index.ts` on `spike/payload-v4`). It relies on plugin internals that every plugin upgrade re-checks: the `/payments/stripe/confirm-order` handler found in `payload.config.endpoints` (fed `req.data` with `paymentIntentID`, `cartID`, `customerEmail`, `secret`), the guest cart `secret` read with `payload.db.findOne`, and the `finalizeOrder` callback the plugin passes to the adapter's `confirmOrder`.
- Rule (S17, S18, S26): the plugin's own webhook endpoint answered 200 and did nothing when `webhookSecret` or `secretKey` was missing or the `stripe-signature` header was absent. With the shop on, startup fails if `STRIPE_SECRET_KEY` or `STRIPE_WEBHOOKS_SIGNING_SECRET` is missing (S17), and S18 replaced the adapter's `/webhooks` endpoint with the shop's own, where a request without a signature, or with a bad one, gets 400 and creates nothing (tested). S26 checks that an unsigned POST to the demo's webhook URL gets 400.
- Rule (S17): `transactions.stripe.paymentIntentID` gets `unique: true` through `stripeAdapter({ groupOverrides })` (tested in the spike). The atomic claim remains the database guarantee of one order per payment; the index stops a second transaction for one PaymentIntent. When S17's wrapper updates the transaction after `initiatePayment` (to store `subtotal` and `shippingAmount`), it checks that the update matched exactly one document.
- Built in S18:
  - Order fields (`collections/Orders.ts`): `accessToken` is 32 random bytes, base64url (43 characters). It is filled by a `beforeValidate` field hook on create (whatever the data said), is never `required` or `unique` (validation runs before `beforeChange`, and nothing may throw in settlement), is hidden from the admin, and is readable only by staff through the API. The fields also include `subtotal`, `shippingAmount`, `needsAttention`, `attentionNote`, and `linePrices` (each line's unit price and total as charged, copied from the transaction, because the plugin's `items` carry no prices). Statuses: `processing` ("paid, to ship"), `shipped`, `cancelled`, `refunded` (the status only: refunds are done in Stripe). Staff change the status, the flag and the note; what was bought or paid is read-only. Nobody creates an order by hand, and only the owner deletes one.
  - Stock: `orders/stock.ts`. Before the claim, `stockShortfalls` notes what the stock can't cover. After it, `clampOversold` runs `UPDATE … SET inventory = 0 WHERE id = ? AND inventory < 0` (atomic) and flags the order whose call clamped. Only the call that created the order clamps: the wrapper puts a random `settlementKey` in its `orderData`, and only the call whose key the order carries is the creator, so a late or losing confirmation never flags its order for another payment's oversell.
  - What can't be deleted for good (`collections/keepReferenced.ts`): a product that an order bought or an unsettled payment is for, and a cart that a payment not settled yet is for (`pending`, `processing`, and also `expired` or `failed`, which `finalizePayment` reopens when Stripe was paid after all, S26). A deleted product would empty the lines pointing to it, and a deleted cart would leave a paid payment that can never be settled. A guest can delete their own cart with its secret. Moving a product to the trash still works. This applies to deletes made by a person (the admin, the REST API). Scripts without a user (the seed's `--force` wipe, S26's reset) are not stopped: they delete the orders too.
  - Orders keep their `createdAt` on update, and their status can't be cleared (an empty status keeps the previous one). With three or more payments racing for the last unit, two decrements can land before either clamp, so fewer orders may be flagged than were oversold. Accepted: stock still ends at 0, and at least one order is flagged.
  - Webhook: the shop's own endpoint (`payments/stripe/webhook.ts`) replaces the adapter's. No `stripe-signature` header, or a bad one: 400. `payment_intent.succeeded` runs `finalizePayment`. A PaymentIntent with no transaction here gets 200 (ignored). A settlement that fails gets 500, so Stripe retries. Other events get 200.
  - `finalizePayment` throws `UnknownPaymentError` (not this shop's), `OrderDeletedError` (settled, but its order was deleted since; the webhook answers 200) or `PaymentNotSettledError` (not paid, or settled elsewhere right now). The browser's return path (`checkout/confirm.ts`) calls it too, after its ownership and Stripe-first checks. When it loses to a slow winner, it waits read-only for up to 3 s for the order before falling back to "payment received".
  - The S19 seam: `onOrderFinalized(payload, order)` (`orders/finalized.ts`). `finalizePayment` calls it every time it returns an order, the already-settled early return included, outside the settlement and in a try/catch. It may run more than once per order, so S19 claims `confirmationEmailSentAt` atomically there before sending.
  - Payments left behind (S26's nightly job): `reconcilePayments(payload, { now?, staleAfterMinutes = 30, expireAfterHours = 24, limit = 100 })` in `orders/reconcile.ts`. It acts on transactions `pending` or `processing`, untouched for 30 minutes, oldest first, at most `limit` per run:
    - `pending` and paid at Stripe: settled.
    - `pending` and unpaid after a day: marked `expired`. If it is paid after all, `finalizePayment` puts it back to `pending` (atomically) and settles it, and the same for `failed` (S26: a night with the wrong Stripe key closes real payments as unknown).
    - `processing` with an order already referencing it: marked `succeeded` and the order flagged. When the order has fewer lines than were charged, the note lists the lines from `linePrices` and says stock and cart were not updated. `onOrderFinalized` then runs, because no webhook may come again. (A product deleted for good mid-settlement used to cause this; such deletes are now refused, as above.)
    - `processing` with no order: atomically reset to `pending`, then settled. The plugin refuses a second order for a transaction that already has one.
    - Never settleable here: no PaymentIntent, or one Stripe doesn't know, is marked `failed`. One paid at Stripe whose cart is gone gets an `attentionNote` on the transaction once, plus an error in the log ("create the order by hand, or refund it in Stripe"), and is not looked at again; the webhook then answers 200 for it, as retrying can't help (S26). S26: make the owner see flagged transactions, and keep the nightly cart cleanup away from carts with unsettled payments (a script delete isn't refused).
    It returns what it did, one result per transaction.
  - "Empties the cart" in the ticket: the plugin marks the cart bought (`purchasedAt`) instead, and a bought cart counts as no cart (S16).

### Email (S07, S19)

- Modules send through `payload.sendEmail({ to, subject, html, text })`. S07 configures the transport from env.
- `src/modules/shop/emails/orderConfirmation.ts`: `renderOrderConfirmation(order: Order, locale: Locale): { subject: string; html: string; text: string }`
- `src/modules/shop/emails/ownerNotification.ts`: `renderOwnerNotification(order: Order): { subject: string; html: string; text: string }` (in the default locale)
- Built in S19: both end with `email.notice` when light.config.ts sets one. Sent once per order from the `onOrderFinalized` seam, after the response during a request (Next's `after`). A failed send keeps its claim (at most once) and flags the order. `sendMissedOrderEmails` (`emails/missed.ts`, run as the last step of `reconcilePayments`) sends them for a paid order, at most 3 days old, whose emails were never claimed (the server stopped before); an order claimed but never sent (killed mid-send) can't be told apart from one sent, so it stays at most once.

### Database schema (S02, S08, S24, S26)

- Development: `next dev` pushes the schema (tests too: `startPayload` boots on a fresh file and pushes).
- Migrations (S26): `src/migrations/`, starting with the baseline `20261104_103848_baseline`. `src/migrations/index.ts` lists them and `src/core/db.ts` passes them as `prodMigrations`, so a server with `NODE_ENV=production` (the Docker image) applies pending ones when Payload initialises: in the Next server that is the first request that needs Payload (`/healthz` doesn't), which waits for them. A new volume gets all its tables that way: no push. The migration files and `index.ts` are generated, never edited by hand (ESLint skips them).
- A PR that changes the schema adds a migration, after rebasing on `main`: `pnpm payload migrate:create <name>` with both modules on, and commits the new `.ts`, its `.json` snapshot and the regenerated `index.ts`. It compares the code's schema with the latest snapshot in `src/migrations/`, not with a database, so any dev database works. `tests/core/migrations.test.ts` fails when the latest snapshot doesn't match the schema, the same comparison.
- Never push the schema into a database a container serves: a pushed database gets a `dev` row in `payload-migrations`, and `payload migrate` (and so the server's start) stops at "you've run Payload in dev mode" instead of migrating. So one-off jobs on a container's database (the seed, the nightly reset, `payload migrate`) run from the image's `schema` stage with `NODE_ENV=production`, which applies pending migrations and never pushes. `scripts/docker/push-schema.ts` is left for a development database only.
- A database made by a push can't be migrated: start it fresh (migrations on a new file, then the seed). The demo was started fresh this way in S26.
